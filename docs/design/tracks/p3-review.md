## Sub-Steps

Each finding was confirmed against the code before it was fixed.

- [x] P3R.1 Runs are hidden until they start, and `prepare` finishes without its client (one medium, one low finding). A reserved run was visible before `prepare` ran: `GET /chats/{id}/stream` attached to its buffer and `GET /api/events` listed it, and a failed `prepare` then left the attached stream open forever (the subscription kept the buffer and its sender alive) and the event stream with `run.started` and no `run.finished`. Runs now start when `launch` starts them (`Reservation::start`, or with their first event, whichever comes first, once); until then `attach` answers idle (`204`) and `watch` lists only started runs that have not sent `done`. Dropping a reservation whose run started but never sent `done` ends its streams with `error` (`INTERNAL_ERROR`) and `done` (`RunSink::close`), so `launch` no longer does that itself; one that never started ends silently. The turn routes run `prepare` and the launch on a task of their own and await its `JoinHandle`, and Run now does the same with `fire`, so a client that disconnects once `prepare` may have written can no longer leave a message, a decision, or a scheduled chat without its run. Tests: registry tests (a run being prepared is idle to `attach` and missing from `watch`, a failed `prepare` announces nothing, `start` announces once; a started run dropped before `done` ends its attached stream with `error` and `done` and its owner hears `run.started` then `run.finished`); a `make test-db` flow test that holds the chat row so `prepare` waits, drops the request after 300 ms, checks that the stream route answers `204` meanwhile, then frees the row and sees the turn answered (it fails with the old inline `prepare`).
- [x] P3R.2 Streams read the replay buffer in place, with per-user stream caps and a run buffer budget (one medium, one low finding). Every attached stream copied the whole replay buffer at subscribe (and again after lagging), so a few hundred idle attaches to a large run held gigabytes. A `Subscription` now keeps an index into the shared buffer and reads one event at a time under the lock; a long merged delta goes in pieces of at least `REPLAY_CHUNK_BYTES` (64 KiB, or what is left) that end where one of its deltas ended, each with that delta's `seq`, so a stream holds about one piece at a time and still never repeats or skips text. `helpers::streams` (`Streams`, `Ticket`) caps the long-lived streams per user: `CHAT_STREAMS_PER_USER` (16) run streams and `EVENT_STREAMS_PER_USER` (8) event streams; one more ends that user's oldest. The per-user event channel lives with the user's event streams, so `watch` no longer walks every user's channel. The sink counts what the buffer keeps (text, 4 bytes per delta end, 64 bytes per event, and audio or tool payloads) and stops the run (`api.runs.buffer.full`) past `RUN_BUFFER_MAX_BYTES` (32 MiB, across all its answers). Tests: a 200 KB merged delta replays in pieces that end on delta boundaries with the right `seq` values, also after a `seq` inside a piece; the buffer counts each delta end, and passing the limit cancels the run; the seventeenth run stream and the ninth event stream end the user's oldest; `Streams` unit tests (only the user's oldest ends, an ended stream never frees a place it no longer holds, what the streams share lives as long as they do); the existing lag, replay, and merge tests adjusted to the lazy read (a stream now sees deltas merged after it attached in the same piece).
- [x] P3R.3 Scheduled-run slots are shared fairly, and scheduled runs stop after 30 minutes (medium). One user could hold both scheduled-run slots (two Run now calls, even on one schedule) for as long as their provider streamed, while other users' due schedules waited. `ScheduleRepository::due` and `ScheduleService::fire_due` take the owners who hold a slot (`RunRegistry::holders`): owners take turns (`ROW_NUMBER() OVER (PARTITION BY user_id)`, each owner's oldest due schedule before anyone's second), and busy owners come after everyone else. `RunRegistry::reserve_now` reserves a Run now and its slot atomically and answers `SCHEDULER_BUSY` while the caller holds a slot already ("One of your schedules is running. Try again when it finishes.") or both are taken; the scheduler reserves each claim itself, and `fire` takes the reservation. A scheduled run still live after `SCHEDULED_RUN_MAX_SECS` (1800) is cancelled, saves its partial answer, and is recorded as failed (`RUN_TIMED_OUT`). Tests: a `make test-db` repository test of the turn order with and without busy owners; a core test of `fire_due` taking turns and putting busy owners last; registry tests of `reserve_now` (one slot per caller, a claimed fire counts, `holders`); a unit test of the time limit (`scheduler::ended`: cancelled and failed past the limit, untouched within it, and the message names the limit); a `make test-db` scheduler test where Alice's live Run now keeps a second Run now of hers `SCHEDULER_BUSY`, and her other due schedule and Bob's come due together: Bob's takes the free slot, hers fire at the next tick.
- [x] P3R.4 Web fixes (one medium, two low findings). Removing an attachment chip while its file uploads no longer leaks the file: when the upload resolves for a chip that is gone, the composer deletes the stored file (`uploaded` in `components/Chat/composer.ts`). Escape no longer closes a dialog while its action runs: `Modal` and `ConfirmDialog` prevent `cancel` while busy and reopen when a browser closes anyway (`components/Dialog/dialog.ts`), and forms inside a `Modal` keep it open while they save (`useModalBusy`: the model picker, chat instructions, move to project, rename project). The chat view shows a spinner while its messages load and their error with a retry when none could be read (`conversationQuery`), instead of an empty conversation with an enabled composer; a streaming turn still shows itself, and an error after messages were read stays above the composer. Tests: `uploaded`, `holdWhileBusy`, `afterClose`, and `conversationQuery`.

## Decisions

- **Visible at launch, not at the first event.** The finding offered three fixes; skipping entries until their first event would have made a Run now's chat answer `204` right after the route returned (the engine may not have emitted yet). `launch` starts the run synchronously before it spawns the engine, so a Run now's `chatId` always attaches, and a run still being prepared is idle to streams. The p3-1 decision (a reservation whose `prepare` fails announces nothing) holds.
- **The newest stream wins.** Past the per-user cap the oldest stream ends instead of the new one being refused with `429`: streams a client left behind (a network that dropped without the server noticing) are the oldest, so they go first and never lock a device out, while one account still holds at most 16 plus 8 streams. A live client whose stream ended connects again (run streams with `?after=`, event streams after 1 second).
- **Run now stays on the slots, one per caller.** Moving Run now to its caller's `MAX_ACTIVE_RUNS_PER_USER` would undo the P3.2 decision that the server never runs more than two unattended runs. Instead a caller who holds a slot (a Run now or a claimed fire) waits, and claims serve other owners first. A single user can still have both slots used by claims when nobody else's schedule is due; the 30-minute limit bounds how long another user then waits.
- **The run buffer stops the run, it does not error the answer.** Passing `RUN_BUFFER_MAX_BYTES` cancels the run's token, so the engine saves the partial answer as `cancelled` like a stop (logged as `api.runs.buffer.full`). Only a provider that streams tiny deltas through a long tool loop reaches it; an honest answer is capped far below by `ANSWER_MAX_BYTES`. Spoken audio (P4.1) counts against the same budget; P4.1 checks that a tool loop with audio stays under it.
- **The time limit is in the API, the rule in core.** `SCHEDULED_RUN_MAX_SECS` and `RUN_TIMED_OUT` are core values; the scheduler's recording task enforces them (it owns the run's task and token), as the registry enforces `MAX_ACTIVE_RUNS_PER_USER`.
- **Forms hold their `Modal` through a context.** `useModalBusy(pending)` lets any form inside a `Modal` keep it open while it saves, so the busy state does not have to be lifted out of each form.

## Not Changed

- Aborting an upload whose chip was removed (an `AbortController` per file) was offered as optional; the file is deleted when its upload resolves, which closes the leak without changing `uploadFile`.
- Files a user attached and uploaded but never sent stay on the chat when the page is left, as before (draft attachments); only removed chips are cleaned up.
