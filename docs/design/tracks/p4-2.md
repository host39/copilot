## Decisions

- **Tap to start, Stop to end.** Push to talk means one bounded clip the user starts and stops, as opposed to live voice. Holding the button was left out: a permission prompt interrupts a hold, and a long press opens the context menu on Android.
- **The clip is an attachment.** After Stop it joins the attachments like a picked file, uploads at once, and its chip has the browser's player, so the preview, removal (which deletes the uploaded file), upload progress and failures, and the "Audio is not sent to this model" warning all reuse the composer's file rules. The server turns an audio chat file into an `audio` part.
- **The cap is exact.** A clip holds at most 4,800,000 samples (300 seconds at 16 kHz); the server refuses chat audio longer than `AUDIO_CLIP_MAX_SECS` and accepts exactly 300 seconds. Clips under 300 ms are dropped as a slip of the finger.
- **The worklet is a file in `public/`.** The web CSP is `script-src 'self'`, so a Blob URL module would be refused; `public/audio/recorder.js` is served from the app's origin (and copied into the native bundle). It only mixes to mono and batches; resampling and encoding stay in TypeScript, where they are tested.
- **The page resamples, not the browser.** An `AudioContext` at 16 kHz would resample in Chrome, but Firefox refuses to connect a microphone to a context at another rate. A box filter (the average of the input each output sample covers) handles any pair of rates and keeps most aliasing out of speech.
- **Microphone messages say what to do.** Blocked (`NotAllowedError`, `SecurityError`): allow it in the browser's site settings. Missing (`NotFoundError`, `OverconstrainedError`): connect one. Busy (`NotReadableError`, `AbortError`): another app may be using it. A page over plain HTTP (not localhost) hides `navigator.mediaDevices`, so the message asks for HTTPS before trying. The microphone button stays visible for `audioIn` models so the message can be read.
- **`pcm16` deltas are 24 kHz mono little-endian** (OpenAI's format, core's `AUDIO_OUT_SAMPLE_RATE`). Each delta becomes an `AudioBuffer` at 24 kHz, which the browser resamples on playback; other formats are skipped.
- **Only turns started on the page speak.** The click that sends, regenerates, retries, or decides makes the audio context (browsers start audio only after a gesture). A run attached to on opening the chat, or started by another device or a schedule, stays quiet; its saved reply has a player. A replay after a dropped connection plays nothing twice (the last played `seq`). Audio already queued plays to its end after `done`.
- **Speak replies lives in the composer** (the spec's Composer line) and is the chat's `voiceReplies` setting, changed at once like the tools menu, so it is also the chat setting the step names. It shows only for `audioOut` models; a new chat sends `voiceReplies: true` only when the draft turned it on for such a model.
- **One sound at a time.** Starting a saved recording stops a spoken reply or another recording, and a spoken reply stops a recording that plays (`claim`).
- **A spoken reply's transcript is its text.** The server keeps the transcript as the text part and adds the audio part, so the transcript under a spoken reply's player shows only when the answer has no text. A voice message's transcript (when a provider returns one) shows under its player.
