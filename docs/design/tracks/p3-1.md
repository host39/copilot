## Decisions

- **Stale tool lists keep their fetch time.** `stale` sets the stored list's `ttl_ms` to 0 instead of moving `tools_fetched_at`, so Settings still shows when the list was fetched and the list stays as the fallback when listing again fails. A fresh listing replaces it as usual.
- **`can_reason` is the capability, not a level.** It is true for every model with the `reasoning` capability (after overrides). Only the Anthropic adapter reads it today; OpenAI-compatible dialects have no "show the default reasoning" switch.
- **Shutdown lets runs finish first.** The spec had the root token fire on the signal; runs now get `SHUTDOWN_GRACE_SECS` (5) to finish on their own (a short answer completes instead of being cut), then the root token fires as before. Both waits count from the signal, so the second call (from `ApiContext::close`) only waits for what is left.
- **`SERVER_STOPPING` is a `422`.** `DomainError` has no `503` variant, and the other registry refusals (`CHAT_BUSY`, `TOO_MANY_RUNS`) are `422` too.
- **Resuming needs no run id.** A `seq` above the running turn's last one cannot be from it, so the stream starts over; a lower `seq` from an earlier run cannot be told apart, and the client's reducer (P3.3) restarts from the beginning when the first event names a message it does not hold.
- **Recovery does not move the chat.** `recover` changes only the messages, so a restart turns no chat unread and reorders nothing.
- **The sink publishes run events, from the engine's outcome.** The spec had the run publish `run.finished` after it released the chat, so a run started right after `done` could announce itself before the last one finished. The sink now publishes `approval.pending` and `run.finished` at `done`, before it frees the chat, and needs the outcome for that: `TurnSink::ended(&TurnOutcome)` is a new port method with a default, so the recording fake and any other sink need nothing (a serial interface change to a frozen port, made here in P3.1). `run.started` comes with the run's first event, so a reservation whose `prepare` fails announces nothing, and scheduled runs (P3.2) get the same events without more code.
- **`run.started` may repeat on connect.** A new stream lists the live runs after it subscribes, so a run that starts in between is never missed but may be announced twice. Clients treat `run.started` as idempotent. Avoiding the repeat would need the users lock held across the run's buffer lock, the reverse of the order the sink takes them.
- **User events are not replayed.** They carry no `seq`; a stream that falls 64 events behind ends, and the client connects again and reads the chat list afresh. Streams also end after `EVENTS_STREAM_MAX_SECS` (15 minutes), so a session signed out on another device stops hearing within that time (rustauth's guard checks a token when a request starts, not during a long stream).
- **`chat.updated` comes from the chat routes only.** Create, update, read (other devices clear the unread mark), save as project, and delete publish it; a run's new messages are `run.finished`. `schedule.updated` comes with the scheduler loop (P3.2), which owns schedule runs, failures, and pauses.
- **Integration tests use wiremock with one mock per completion.** Each scripted answer is mounted with `up_to_n_times(1)`, so completions answer in order; one answer is delayed (`set_delay`) to keep a run live while an event stream connects.
