## Decisions

- **Scheduled runs have their own limit.** Scheduled fires and Run now take one of the `MAX_SCHEDULED_RUNS` (2) slots and do not count against their owner's `MAX_ACTIVE_RUNS_PER_USER` (3). A claimed fire then never fails because its owner is chatting (the claim has already moved `next_run_at`), and a user's chats never wait for their schedules. They still go through the registry: one run per chat, stop, drain, and the same events.
- **Run now shares the slots.** "Behaves exactly like a scheduled fire" includes the limit, so the server never runs more than two unattended runs. Run now answers `SCHEDULER_BUSY` (422) while both are taken instead of queueing; the button shows the message.
- **Slots before claims, the chat id before the chat.** A tick takes its slots first and claims at most that many, so a claimed fire always has a slot; the firing carries its chat id, so the run reserves its chat before `prepare_scheduled` writes it. The one gap left is shutdown: a claim made just as draining starts cannot reserve, is logged as `api.scheduler.run.skipped`, and records nothing (its next fire runs as usual). Ticks claim nothing once draining has begun.
- **A missing model pauses at the fire.** Deleting a provider and turning a model off already pause schedules (`disable_for_model`); a model that a refresh marked unavailable, or a connection turned off, now pauses the schedule when it next fires, with the reason in red, instead of failing three times. A run that could not start for any other reason (a project over the model's context, a key that no longer opens) counts as a failed run.
- **Run now records like a fire.** Its outcome raises or resets the failure count, a pause pauses the schedule, and a start failure is recorded and answered with the error.
- **A stopped run is a failure.** The spec's `RunOutcome` mapping already made a cancelled answer `Failed("The run was stopped.")`; that holds for a run the user stopped and for one a shutdown cancelled.
- **`schedule.updated` after the claim and after the record.** The Scheduled page sees the next run move at once and the outcome when the run ends; the run's own `run.started` and `run.finished` come from its sink like any run.
- **The loop uses the system clock; tests tick at chosen instants.** `Scheduler::tick(now)` takes the time, so the database tests fire schedules a second before and after their next run without waiting.
