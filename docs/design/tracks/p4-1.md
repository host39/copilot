## Decisions

- **Audio parts were already in place.** P1.3 and P2.B built most of the path: `prepare` turns an audio chat file into an `audio` part, lowering sends it as `LlmPart::Audio` to `audio_in` models and as a notice otherwise, the adapters send `input_audio` (OpenAI-compatible, `wav` and `mp3`) or refuse audio (Anthropic), and `context::request` sets `audio_out` for `audio_out` models with Speak replies on. P4.1 adds what was missing: the length limit, the saved reply, and the end-to-end tests.
- **Gemini audio in works through the compatibility endpoint.** The spike's fixture and the route test send `input_audio` WAV there; Google documents it. No preset default turns `audio_in` on (the spec keeps no model-family table), so the user enables it per model. Gemini's compatibility endpoint documents no audio output, so `audio_out` stays off by default; it is not locked, because a future model may support it.
- **One limit for audio in a chat.** `AUDIO_CLIP_MAX_SECS` (5 minutes) covers recorded clips, uploaded WAV and MP3 files, and spoken replies (`AUDIO_OUT_MAX_BYTES` is the same length at 24 kHz). It is checked at upload, where the bytes are, so no column stores a duration. A file whose container does not say how long it plays passes (the size limit still applies). Changed in [`p45-review`](./p45-review.md): the length now follows what decoders play (a WAV file's frame size from its one `fmt` chunk, an MP3 file's counted frames), and chat audio whose length cannot be measured is refused. The check accepts exactly 300 seconds, which the web client's cap produces.
- **The transcript is the text.** A spoken reply's transcript is its text part (search, copy, and replay use it); its `audio` part carries no transcript, so lowering never sends the transcript twice and never sends the audio. A user clip's transcript stays null: Chat Completions returns no transcript of the user's audio.
- **Saved on every exit.** A stopped, failed, refused, or paused answer saves the audio it streamed, like its text. The audio part is the answer's last part, so the stream's part indices match the stored parts; `part.started` for it comes after the stream, once the file exists.
- **The upload rules apply to replies.** Saving goes through `FileService::upload`, so a reply larger than `MAX_UPLOAD_MB` or past the storage quota is not saved; the answer keeps its transcript and the failure is logged with its code.
- **`pcm16` means 24 kHz.** OpenAI's `pcm16` output is 24 kHz mono 16-bit little-endian; OpenRouter passes OpenAI's audio models through. The WAV header states 24 kHz, and the web player (P4.2) plays deltas at that rate.
- **Duration of user clips.** `durationMs` is null for uploaded clips (the browser's player reads the WAV header); spoken replies have it.

## Follow-Ups

- Regenerate, retry, and edit delete messages but not the chat files their parts name (spoken replies, tool result images, the attachments of an edited message). Done in P6.1 ([p6.1-server.md](./p6.1-server.md), P61S.3).
