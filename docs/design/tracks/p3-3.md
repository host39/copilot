## Decisions

Part 2:

- **The events reader reconnects like `EventSource`.** 1 second after the server closed the stream (it ends every 15 minutes), after a failure with the reattach backoff (1, 2, 4, 8, then 15 seconds; an open stream resets it), at once when the device is online again or the page visible, every 5 minutes while the server has no event stream (`404`, `501`, or another `4xx`), after a `429`'s wait, and never after a `401` (the client signs out). A stream that opens again refreshes every list, since events are not replayed.
- **Events never refresh a chat's messages.** Reading them marks the chat read (and `chat.updated` follows), so the shell refreshes only the lists, the changed chat alone (`exact`), and schedules. The chat page rereads its own messages on `run.finished` and `approval.pending`, and only while it follows no stream.
- **Back closes dialogs through the platform.** Every overlay is a modal `<dialog>`, which Chrome on Android closes on back by itself (close requests). History entries per overlay were left out: closing one by other means would need `history.back()`, which races a navigation that follows (Save as project, Delete). The native app registers Tauri's `onBackButtonPress` and closes the topmost dialog with `requestClose` (else a cancelable `cancel`, then `close`), so a busy dialog can stay open. Leaving the app calls `exit` from `@tauri-apps/api/app`; Phase 5's capabilities must allow it (deferred to P5.1).
- **The chat list goes beneath a deep link** only on narrow screens (below `lg`, where the sidebar is a drawer) and only on the first entry of the app's history (React Router's `idx` 0), so back from a shared chat link reaches the chat list before it leaves.
- **Shortcuts accept Cmd on a Mac**, wait while a dialog is open, and skip keys an input method composes or another handler took. Ctrl+K on the search page focuses its field instead of clearing the query.
- **Uploads take the `XMLHttpRequest` path only when they ask for progress** (`onUploadProgress`) and the transport has one; everything else, and every native request, goes through `fetch`.
- **Run now opens the run's chat**, which attaches to the run. Until P3.2 writes the route it answers `501`, and the button shows the server's message.
- **The schedule's target is fixed once created** (the update body has no `projectId`); the form shows it as text when editing. A standalone schedule shows Instructions; a project schedule shows the on-ask choice with the target's `ask` tools instead, since standalone runs have no tools.
- **The form keeps every preset's value** while the user switches presets, and switching to Custom starts from the rule the preset wrote. A saved rule a preset cannot write exactly opens as Custom.
- **The tools menu stores overrides only where the chat differs from its project**, so checking a project server again removes the override; built-in tools are stored as the chat's own list once changed. The new chat draft sends tools only when changed, so a project chat keeps following its project.

Part 1:

- **Reattach keeps the run it holds.** A dropped connection attaches with `?after=<last seq>`. The first event then decides: a `seq` at or below the last one means the server replayed from the start, so the run is rebuilt from scratch (a replay merges deltas, which must never be added to text already shown); an event naming a message the run does not hold belongs to another run, so the client attaches again without `after`; anything else continues. `message.started`, `error`, and `done` always continue, so a new run whose first event after `after` starts a message shows only its later messages until `done` reloads the saved ones.
- **Saved messages win once final.** The timeline shows a saved message the run is still writing (`streaming`) as the run's copy, and any other saved message as saved. The user's message shows until the saved list holds a user message after the last one kept when the turn started. Edit, regenerate, and retry hide the messages they replace until the saved list no longer holds them.
- **Decisions go together.** The decisions route takes exactly the pending calls, so the cards collect one decision per call and send them once all are chosen; a choice can change until then. The cards close at once (the cached message is updated the way the server records decisions) and come back from the server if it refuses. Built-in tools always ask, so they offer no "Approve for this chat".
- **Attach is always shown.** The step's text said attachments show only when the model allows; the spec (Capability Display) shows attach always and warns on a file the model cannot read, and the spec wins. The microphone, the only control hidden by capability, comes with voice (P4.1).
- **Edit works on any user message**, as the spec says, and sends the message's files again.
- **New chat attachments** are uploaded after the chat is created; a send that fails part way keeps the chat and the files already uploaded, so sending again creates nothing twice.
- **A run error without a failed answer** (nothing was saved) stays as the page's alert after the run ends.
- **Reconnects** wait 1, 2, 4, and 8 seconds, then 15 between tries, and try at once when the device is online again or the page visible. An idle page also looks for a run then (another device may have started one) until `GET /api/events` reports runs.
- **Leaving the page only stops reading.** The abort waits a tick, so React's strict mode remount keeps the stream.
- **Esc stops** the answer being written unless a dialog is open or a field used the key.
- **Spoken audio** (`audio.delta`) is not played yet: voice is P4.1. Tool result images show as files to download, not inline.
- **Live tool calls carry their title** from `tool.requested`; saved calls show the tool's name (messages do not store titles). Server names come from `GET /tool-servers`.
