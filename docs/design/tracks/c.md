## Sub-Steps

- [x] P2.C.1 `copilot-mcp` implements `ToolHost` and `ToolSession` with rmcp 3.12 over the injected hardened client (`Outbound::pick` on the endpoint's URL and scope; the composition root passes `clients(Purpose::Tools)`). Dual-era: a server with no known revision gets rmcp's `Auto` lifecycle (`server/discover` for 2026-07-28, then `initialize` with `Mcp-Session-Id` sessions for 2025-11-25 and older); a probe that finds only legacy revisions behind `server/discover` falls back to `initialize`. Era memory: the negotiated revision is remembered per server id and URL for the life of the process (at most 4,096 entries), and the endpoint's stored `protocol_version` is used when the process has none, so a legacy server skips the modern probe; a remembered revision the server no longer speaks falls back to the probe. Credentials: the sealed bearer token and custom headers go on every request as sensitive headers. Listing: every page of `tools/list` (at most 16 pages and `MCP_RESPONSE_MAX_BYTES` of definitions in all), the smallest page `ttlMs` as the cache hint (none when a page has none), `readOnlyHint` kept as a hint, titles from the tool or its annotations; rmcp's own response cache is off, since core keeps the list. Caps: `MCP_RESPONSE_MAX_BYTES` on every JSON response and SSE event (rmcp refuses a larger one instead of buffering it); core cuts result text to `MCP_RESULT_MAX_BYTES`. Calls: one connection per server per run, opened on its first call (a failed connection fails the run's later calls to that server without trying again; a connection whose transport ended is opened again); each call's timeout covers connecting, the call, and a refresh, fails with `TOOL_TIMEOUT`, and dropping the request cancels it on the server. Unknown-tool refresh: a JSON-RPC `-32602` (unknown tool or invalid arguments) or `-32020` (header mismatch) makes the session list the tools again on that connection, which also gives rmcp the input schemas it needs for `Mcp-Param-*` headers; a tool still listed is called once more after a header mismatch, and one that is gone fails with `TOOL_UNKNOWN`. Results: text, base64 images and audio (undecodable ones become binary notices), resource links and blob resources as links, embedded text resources as text, `structuredContent` as JSON text only when there are no content blocks, `isError` kept. Failures are readable `502` errors with stable codes (`TOOL_SERVER_BLOCKED`, `_AUTH` with a sign-in message when no credentials are set, `_UNREACHABLE`, `_TIMEOUT`, `_TOO_LARGE`, `_HTTP` with the status, `_PROTOCOL`, `_REFUSED`, `_HEADERS`, `_FAILED`), logged as `mcp.http.blocked` or `mcp.http.failed` with the server id, a failure kind, and the status; bodies, addresses, and credentials are never echoed or logged, and a server's JSON-RPC error message reaches a call result only as one line of at most 300 characters. Tests: unit tests (lifecycle choice, stored revisions, error classification and messages, content mapping, era memory) and `tests/mcp.rs` against an in-process rmcp server (dev-dependency, served by axum on loopback) in four shapes: modern, modern-only, legacy with sessions whose `server/discover` gets a plain `400`, and legacy behind `server/discover`; JSON and SSE responses. They cover paged listing with `ttlMs`, both eras with the discover, initialize, and session counts, era memory in one process and from the stored revision, a stale remembered era, the bearer token and a custom header on every request, rejected and missing credentials, three calls on one connection per era (text, image, tool error), a timeout that cancels the request on the server and leaves the connection usable, an oversized response over JSON and over SSE (then a new connection), a tool list over the cap, a header mismatch listed again and retried, a removed tool failing with `TOOL_UNKNOWN` without a retry, SSRF refusals through the hardened client (plain `http` for a public-only connection, `localhost` and `127.0.0.1` over `https` for a public-only connection, the metadata address for any connection) with nothing reaching the server, an unreachable server, a call outside the run, and a non-MCP URL whose body is never echoed.

## Interface-Change Requests

None blocking. For a later serial step:

- **Unknown tools in the stored cache.** The spec refreshes the stored tool list "when a call reports an unknown tool". The adapter refreshes rmcp's list on the connection and fails a removed tool with `copilot_mcp::TOOL_UNKNOWN`, but the engine treats it as any call error, so the stored list stays until its `ttlMs` (or an hour) passes or the user tests the server. A `TOOL_UNKNOWN` constant next to `TOOL_TIMEOUT` in `core/src/ports/tool_host.rs`, and a hook that marks the server's cache stale when a call fails with it (for example `ToolService::stale(actor, server)` clearing `tools_fetched_at`), would close the gap.
- **Adapter time limits as core constants.** `copilot-mcp` keeps its connect (15 s per attempt), listing (30 s, connecting included), and close (5 s) limits, and the 16-page listing cap, as its own constants (`copilot_mcp::Limits`). The spec keeps tuning values in `core/src/shared/constants.rs`; moving them there is a small frozen-file change if the owner wants them in one place.

## Notes

- `Cargo.lock` gains rmcp's server-side crates (`schemars`, `ref-cast`, `dyn-clone`, `serde_derive_internals`) for the dev-only in-process server; the production build keeps rmcp's client features only (`cargo tree -e normal -p copilot-mcp` shows no `schemars`).
- When an SSE event passes the size cap, rmcp ends the whole connection and reports only that it ended (`TransportClosed`), so that case reads "The connection to the tool server ended. The server may have stopped, or sent more than Copilot accepts in one response (4 MiB)." with `TOOL_SERVER_FAILED`; a JSON response over the cap gets `TOOL_SERVER_TOO_LARGE`.
- A `tools/call` answered with a JSON-RPC error keeps the server's message (one line, at most 300 characters) in the call's error result, like any other tool output the model sees; a `tools/list` error is never echoed.
