## Interface-Change Requests

None blocking. For a later serial step:

- **Unknown tools in the stored cache.** The spec refreshes the stored tool list "when a call reports an unknown tool". The adapter refreshes rmcp's list on the connection and fails a removed tool with `copilot_mcp::TOOL_UNKNOWN`, but the engine treats it as any call error, so the stored list stays until its `ttlMs` (or an hour) passes or the user tests the server. A `TOOL_UNKNOWN` constant next to `TOOL_TIMEOUT` in `core/src/ports/tool_host.rs`, and a hook that marks the server's cache stale when a call fails with it (for example `ToolService::stale(actor, server)` clearing `tools_fetched_at`), would close the gap.
- **rmcp's own logs.** `copilot-logger` applies one level to every target. rmcp logs free-form messages at `info` (for example "Service initialized as client", and each server notification with its contents), and at `trace` every message it receives, tool results included. Capping the `rmcp` target at `warn` in `copilot-logger` (a frozen crate) would keep untrusted server text and results out of the logs at every level; copilot-mcp's own `mcp.*` events cover what operators need. Done in `p2-review`: `warn` was not enough (rmcp logs a failed connection's URL at `error`), so `copilot-logger` silences the `rmcp` target at every level.
- **Adapter time limits as core constants.** `copilot-mcp` keeps its connect (15 s per attempt), listing (30 s, connecting included), and close (5 s) limits, and the 16-page listing cap, as its own constants (`copilot_mcp::Limits`). The spec keeps tuning values in `core/src/shared/constants.rs`; moving them there is a small frozen-file change if the owner wants them in one place.

## Notes

- `Cargo.lock` gains rmcp's server-side crates (`schemars`, `ref-cast`, `dyn-clone`, `serde_derive_internals`) for the dev-only in-process server; the production build keeps rmcp's client features only (`cargo tree -e normal -p copilot-mcp` shows no `schemars`).
- When an SSE event passes the size cap, rmcp ends the whole connection and reports only that it ended (`TransportClosed`), so that case reads "The connection to the tool server ended. The server may have stopped, or sent more than Copilot accepts in one response (4 MiB)." with `TOOL_SERVER_FAILED`; a JSON response over the cap gets `TOOL_SERVER_TOO_LARGE`.
- The SQL test helper `helpers::testing::tool_server` now writes `https://mcp.example.invalid`, so a route test whose turn lists that server fails at once instead of reaching the network; Bruno's servers already use `.invalid` hosts.
- Track D's tool server screens (`docs/design/tracks/d.md`) expected `502 ADAPTER_UNAVAILABLE` from Test; they now get the adapter's codes and messages above, also as `502`.
- A `tools/call` answered with a JSON-RPC error keeps the server's message (one line, at most 300 characters) in the call's error result, like any other tool output the model sees; a `tools/list` error is never echoed.
