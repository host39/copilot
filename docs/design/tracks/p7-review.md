# P7 Review: Fixes After the Phase 7 Reviews

Branch: `claude/copilot-project-planning-6y3fep` (shared with the other checkout; merged before each push). Base: P7.1 to P7.3 as pushed at `eef9745`. Roadmap step: `p7-review`.

## Status

In progress. Eight findings (two high, four medium, two low) from the combined and security reviews of P7.1 (the Responses API), P7.2 (MCP OAuth sign-in), and P7.3 (stdio servers). Each is confirmed against the code or by running it before it is fixed.

## Sub-Steps

- [x] P7R.1 Responses state replays only to the model that wrote it (high). **Confirmed:** `ReplayContext.same_model` was set only for the `gemini` preset, and the context hash covers the capability flags and the reasoning level but not the model, so on a connection whose models report no metadata (OpenAI's `/models`) every model gets the same flags and the same hash. A chat that moved from a reasoning model to another model on the same connection replayed the earlier answers' output items, encrypted reasoning included, and the current turn replayed whatever the hash (a decision after a model switch). OpenAI refuses reasoning items for a model without reasoning, and since the hash never changes the chat would fail on every later turn. **Fix:** `same_model` is now on for the `gemini` preset and for every connection on the Responses API (`context::same_model`), so Responses state goes back only to the model that wrote it; after a switch the answers are rebuilt from their parts (text and calls with Copilot's call ids), exactly as after an API switch. Chat Completions connections still replay across models (their state is per connection, and Claude drops what a model cannot read). **Fake model server:** a reasoning item's `encrypted_content` is now bound to the model that gave it (`encrypt(model, summary)`); a reasoning item another model gave answers `400`, with OpenAI's "Reasoning input items can only be provided to a reasoning or computer use model" when the request's model has no reasoning. **Smoke:** a new Responses step pauses a `think tool echo` turn on `fake-chat`, switches the chat to `fake-audio`, and approves; it failed with that `400` before the fix (checked by reverting it) and completes with "Tool said: after a switch" now. Tests: `context::tests::responses_state_replays_only_to_the_model_that_wrote_it` (same model replays the earlier answer and the current turn; another model with the same hash replays neither and sends the text; Chat Completions still replays), the fake's Responses router test (another model's reasoning refused, both messages), and `make smoke`.
- [x] P7R.2 Tool server sign-in: mix-up, sign-in links between users, and client secrets (one high, three medium). **Mix-up, confirmed** with a core test of the reviewer's scenario: a server whose discovery names its own issuer and token endpoint, takes client documents, and leaves out `iss` got the shared document as its client, and a code without `iss` that came back to the shared callback with its `state` was sent to its token endpoint. **Fix:** a sign-in with a pre-registered or registered client comes back to `<PUBLIC_URL>/api/oauth/callback/<tag>` (`issuer_tag`: base64url of the first 16 bytes of the issuer's SHA-256; dynamic registration registers that URI), and the callback refuses a flow that came back to any other path. The reviewer also proposed a client document per issuer; that does not help, because the malicious server learns its own document's URL and can hand it to the honest authorization server, whose consent screen then looks right to a victim who just pressed Sign in. The shared document is a client id every authorization server accepts, so it is now used only when the authorization server advertises `authorization_response_iss_parameter_supported`, and its callbacks then need a matching `iss` (the existing RFC 9207 check). **Client secrets, confirmed** with the reviewer's steps: a secret survived a URL change to another origin and went to whatever token endpoint the next discovery named. **Fix:** `tool_servers.oauth_client_issuer` (migration `confirm_tool_server_sign_in`) binds a pre-registered client to the issuer of its first sign-in (`bind_client`, compare-and-set, at the start, before anything is sent); a sign-in that finds another issuer fails with `CLIENT_ISSUER_CHANGED` naming it; saving the client again forgets the binding; a URL change to another origin forgets the client unless the same update sets one, as headers are forgotten. The server's page shows the redirect URI to register once the client is bound (`oauth.redirectUri`), and `CLIENT_ID_REQUIRED` names the issuer and the redirect URI. **Sign-in links between users, confirmed** in the code (`finish` stored the tokens for the flow's user whoever's browser came back), and the recorded mitigation was wrong (consent is not guaranteed: the sender can edit the URL, and authorization servers remember consent for this install's one client document). The reviewer's first fix (an authenticated completion by `flow.user_id`) does not close it on its own, because the sender is that user; the second (a cookie set at the start) leaves the native apps on an unbound path any user could choose. **Fix:** the callback exchanges the code but stores nothing on the server: it replaces the flow with a held one (the tokens sealed, a new confirmation code of 8 letters stored as its SHA-256, a `state` nobody knows, 10 minutes) and sends the browser to `/oauth/done?result=confirm&server=<id>#<code>`. `POST /api/tool-servers/{id}/oauth/confirm` stores the tokens when the server's owner sends that code (5 tries, counted before each comparison, so parallel guesses share them). The done page sends the code itself when its browser is signed in to Copilot (the web app's own tab), so the web flow needs no typing; a browser without a session shows the code with a warning, and the native apps' sign-in panel asks for it. A link the sender passes on brings the receiver's browser back with a code only the receiver sees. Tests: core (`a_callback_holds_tokens_until_the_owner_confirms_them`, `a_sign_in_link_sent_to_another_user_signs_in_nobody`, `held_tokens_expire_and_follow_the_server`, `a_code_from_another_authorization_server_is_refused`, `a_client_secret_stays_with_its_authorization_server`, and the redirect URI and client document cases in the existing tests), `auth.rs` (held round trip, codes, tags), the database (`a_held_flow_waits_for_its_owner_and_counts_tries`, `a_client_is_bound_once_to_its_authorization_server`), the API with a scripted authorization server (the tagged redirect URI, a callback at the bare path refused, the code in the fragment, a wrong code, confirmation; Bob's link opened by Alice: her confirm `404`, Bob's guesses end the flow, Bob's own browser signs him in), route tests for the tagged callback, Bruno `09-34` to `09-38`, contracts (`OAuthConfirmRequest`, `OAuthStatus.redirectUri`), and web tests (the done page with and without a session, a garbled code, the code field, the redirect URI).
- [x] P7R.3 stdio servers: the server's environment and zombies (one medium, one low). **Environment, confirmed:** a program started with an empty environment and the server's user read the parent's `/proc/<ppid>/environ`, `SECRET_KEY` included (the new test's control step does this before hardening, as a user other than root). **Fix:** `copilot_mcp::harden` calls `prctl(PR_SET_DUMPABLE, 0)` (through `nix`, already in the graph through `process-wrap`; `unsafe` stays forbidden), and the composition root calls it when `MCP_STDIO_ENABLED` is on, before the host gets its stdio directory; a failure stops the server from starting. The server's `/proc` files then belong to root and same-user tracing is refused; the programs stay dumpable (`execve` resets the flag). Environment scrubbing after `AppConfig::parse` was not added: changing the environment is `unsafe` in Rust 2024, and the non-dumpable flag covers `mem` as well as `environ`. **Zombies, confirmed:** a new test makes the test process a child subreaper (as PID 1 is), drops a session whose program started a child, and waits for both to be reaped; without the fix the child stayed a zombie (the test failed with "child gone: false"). **Fix:** `Process::drop` now kills the group and starts a thread that runs `waitpid(-group)` until `ECHILD`, as `process-wrap` does when it waits for a group; `stop` already waited for the group. **Not done:** `init: true` in `deploy/compose.yml` (see Decisions). Tests: `tests/stdio.rs` `a_dropped_group_is_reaped_by_its_new_parent` and `a_hardened_server_hides_its_environment` (the second runs its checks only as a user other than root, as CI does; run here with `setpriv --reuid=65534`, where it read the secret before `harden` and got `PermissionDenied` after).
- [x] P7R.4 The native apps' sign-in wait (low). **Confirmed** in `details.tsx`: the wait ended only on `signed_in`, so "Sign in again" on a signed-in server reported "Signed in." at once, and a refused sign-in kept the Sign in button busy (and so disabled) for 10 minutes. **Fix:** the wait records the server's sign-in (`signInMark`: the state and the token's expiry) when it starts and ends when that changes, when the code is accepted, or after 10 minutes; Sign in is busy only while its own request runs, so a refused or abandoned sign-in can start again at once; the code field shows while the app waits (and on a page the done page links to with `?code`). Tests: `apps/web/test/tool-servers.test.tsx` (the mark changes with a new sign-in and a new expiry, the code field, the done page).

## Decisions

- **Same model for all of Responses, not only reasoning items.** Recording the model in the state and dropping only the reasoning items would keep message and call items across a switch, but those carry item ids that point at the dropped reasoning (the API refuses such ids), so they would lose their ids anyway; rebuilding from parts gives the same request with one rule that core already applies to Gemini.
- **No init process in the container.** The reviewer proposed `init: true` (Docker's `tini`) so orphans are reaped. That init starts with the container's whole environment and the same user, and it is an ordinary dumpable process, so a stdio program could read `SECRET_KEY` from `/proc/1/environ`, undoing the fix above. The server stays PID 1, reaps the groups it kills, and the self-hosting guide says not to add an init. A helper that leaves its process group (a daemon after `setsid`) is neither killed nor reaped; `pids_limit` bounds it, and the guide sends such programs behind a bridge.
- **A confirmation code, not a cookie, binds a sign-in to its owner.** A cookie set by the start would bind the web flow invisibly, but the native apps start in their own HTTP client and finish in the system browser, so they would need an unbound path, which any user can pick for a link they want to send. The code works the same for both, and the web app sends it by itself from its own tab. Holding the tokens rather than the code also keeps the authorization server's short code lifetime (often a minute) out of the user's typing time.
- **Pre-registered clients get the issuer's redirect URI too.** A plain shared callback for them would have kept one URI to register, but an organisation's app is exactly where an authorization server skips consent, so a mix-up through it would be silent. The redirect URI is shown where it is needed: in `CLIENT_ID_REQUIRED` and on the server's page after the first sign-in.
- **The client binds at the start of its first sign-in**, not at its first success: the redirect URI can show at once, and the secret is only sent at the exchange, to the token endpoint of the issuer it was bound to.
- **Residual risks recorded in the spec:** an authorization server without `iss` and with open registration of any redirect URI still allows a mix-up behind its own consent screen for a client the attacker names; the confirmation code can be phished like any code.
- **Hardening only with stdio on.** A non-dumpable server also has no core dumps and cannot be traced by its own user, which an operator may want while debugging; without stdio programs no process of the server's user runs inside its container.
