# P7.1: OpenAI Responses API Adapter

Branch: `claude/copilot-project-planning-6y3fep` (shared with other checkouts; merged before each push). Base: P6.4 at `fefa282`. Roadmap step: `p7.1`.

OpenAI's newest models call tools and summarize their reasoning only through the Responses API (`docs/research/providers.md`, Chat Completions vs Responses): GPT-6 Astra and GPT-6.1 Sol need it for tool calling, and from GPT-5.4 on Chat Completions refuses tools with any `reasoning_effort` but `none`. This step adds a Responses adapter to `copilot-providers` and lets each OpenAI-compatible connection pick the API its answers use.

## Decisions

- **A stored per-connection API, not a new kind.** The kind stays the wire family (`openai` or `anthropic`); `providers.api` (`chat_completions` or `responses`, `NULL` for `anthropic` connections, enforced by a `CHECK`) picks the endpoint of an `openai` connection's answers. A new kind would have meant a second preset table, a kind picker change, and a second model listing, while both APIs share `GET {base}/models`, the key, and the base URL.
- **Which presets route where.** The `openai` preset defaults to Responses (OpenAI's newest models need it for tools and reasoning summaries) and may switch to Chat Completions, which still carries audio (`input_audio`, spoken replies) that the Responses API does not take yet ("Coming soon" in OpenAI's migration guide). The `custom` preset defaults to Chat Completions, the one endpoint every compatible server serves, and may opt in (vLLM, LM Studio, llama.cpp, and gateways serve `/responses` too). `gemini`, `openrouter`, and `ollama` stay on Chat Completions: Google documents no Responses endpoint on its compatibility layer, and the OpenRouter and Ollama dialects (`reasoning_details`, `stream_options`) are tuned to Chat Completions. The rule is `OpenAiApi::fits` in core.
- **Existing connections.** The migration moves `openai` preset connections to Responses and leaves every other connection on Chat Completions. Models of `openai` preset connections whose ids start with `gpt-6` get their detected `tools` flag back, because it was only off through the old lock.
- **Detection stored before locks.** A refresh now stores the detected capabilities without applying locks; `Model::effective` applies them. A lock that depends on the API (audio on Responses, `gpt-6` tools on Chat Completions) then follows a switch at once, without a refresh.
- **What replays.** The answer's finished output items (`response.output_item.done`, or the terminal event's `output` for items that never came) are stored as `{"api": "responses", "items": [...]}`: `reasoning`, `message`, and `function_call` items only. A reasoning item without `encrypted_content` cannot go back statelessly, so it is dropped and the other items lose their `id`. On replay the items go out verbatim only when their calls are exactly the message's calls; otherwise, and for a state the Chat Completions adapter wrote (after a switch), the message is rebuilt from its parts. Core's replay rules (same connection, same context hash or the current turn) decide whether the state is offered at all.
- **Reasoning settings.** `reasoning.summary: "auto"` and `include: ["reasoning.encrypted_content"]` go with models that have the `reasoning` capability (`effort` when core picked a level; `effort: "none"` alone when reasoning is off). Models without it get no `reasoning` field, which non-reasoning models reject; OpenAI still returns encrypted reasoning in stateless mode by default, so a reasoning model whose flag is off still replays.
- **No strict mode.** Function tools go with `strict: false`: Responses otherwise tries strict mode, which makes every optional argument of an MCP tool required.
- **Locks.** On Responses, `audio_in` and `audio_out` are locked ("The Responses API takes and returns no audio yet: use Chat Completions for audio models."). The `gpt-6*` tools lock and the forced `reasoning_effort: none` with tools apply only to the `openai` preset on Chat Completions.
