# P7.2: MCP OAuth Sign-In

Branch: `claude/copilot-project-planning-6y3fep` (shared with other checkouts; merged before each push). Base: P6.4 at `fefa282`. Roadmap step: `p7.2`.

Remote MCP servers that require OAuth (a `401` with a `resource_metadata` challenge, then browser consent) did not work in v0.1: a tool server took a bearer token or static headers only. This step adds OAuth sign-in per the MCP authorization specification, revision `2026-07-28` (the current one, checked on 2026-11-27 at modelcontextprotocol.io).

## Decisions

- **Hand-written OAuth client, not rmcp's `auth` feature.** rmcp 3.12.0 (the newest release, 2026-11-26) has an `auth` feature with discovery, CIMD, registration, PKCE, and refresh, but it would cost 14 more crates in the server's graph (210 to 224, measured with `cargo tree -e normal -p copilot-api`), among them second copies of `base64`, `rand`, `sha2`, and `thiserror`; its `AuthorizationManager` owns the flow state and the credentials in its own stores, while Copilot's flow spans two requests (start and callback) with the state in Postgres and the tokens sealed per row; and it takes one HTTP client, while every Copilot request picks its client by URL and the owner's network scope (`Outbound::pick`). The OAuth requests Copilot needs are four (protected resource metadata, authorization server metadata, registration, token), so they live in `copilot-mcp` next to the MCP client, behind core's `ToolAuth` port. No `aws-lc-rs` either way.
- **Auth mode.** `tool_servers.auth_mode` is `none`, `headers`, or `oauth`. Headers exist only in `headers` mode (stored headers switch the server to it, clearing them leaves it), and the OAuth client and sign-in only in `oauth` mode; switching modes drops the other mode's credentials. A `CHECK` holds this in the database too. Requests without `authMode` keep working: credentials imply `headers`.
- **Client id order (the specification's).** A pre-registered client id (and optional secret) entered for the server; else this install's Client ID Metadata Document (`<PUBLIC_URL>/api/oauth/client`) when the authorization server advertises `client_id_metadata_document_supported` and `PUBLIC_URL` is `https`; else dynamic registration (`application_type` `web`, or `native` for a loopback redirect URI); else the error `CLIENT_ID_REQUIRED` asking for a client id. A dynamically registered client is kept in the sign-in (for refreshes) and not reused for the next sign-in, which registers again.
- **Flow state.** A sign-in in progress is a row in `oauth_flows`: the `state` (32 random bytes, base64url) only as its SHA-256, and the PKCE verifier, the recorded issuer, and the token request's parts sealed and bound to the row. A flow lives 10 minutes (`SIGN_IN_FLOW_SECS`), one per server (a new start replaces it), and the callback deletes it before anything else, so a `state` works once.
- **Callback checks.** Unknown or used `state`: expired. Past its time: expired. `iss` present and different from the recorded issuer, or absent when the issuer advertises `authorization_response_iss_parameter_supported`: failed, without acting on `error`. `error=access_denied`: denied. The server must still belong to the flow's user, be in `oauth` mode, and have the URL the sign-in started with. The authorization server's `error_description` is never shown or logged.
- **Tokens.** The access and refresh tokens are sealed in `oauth_tokens_sealed` with the token endpoint, the client, the issuer, the resource, and the scope, so a refresh never discovers again; `oauth_expires_at` and `oauth_refreshable` show the state without opening it. Settings writes never store a sign-in (`save_sign_in` does, compare-and-set on the sealed bytes for refreshes); a settings write clears it only when the mode leaves `oauth` or the URL changes (a token is bound to its resource).
- **Refresh.** An access token within 60 seconds of its expiry (`TOKEN_EXPIRY_SKEW_SECS`) is refreshed before it is sent. A `401` refreshes once and retries. Refreshes of one server run one at a time in the process, and one that finds the token already replaced uses the new one. A refresh the token endpoint answers with an OAuth error (`OAUTH_REJECTED`) clears the sign-in: the server needs sign-in again. Any other failure (no connection, a server error) keeps the sign-in and fails the request.
- **Residual risk: sign-in links between users of one instance.** The callback is public (the browser that comes back carries no Copilot session; in the native apps it is the system browser), so the `state` alone ties it to a flow. A user of the same instance could send another user the authorization URL of a flow they started; completing it would sign the sender's tool server in with the receiver's account at the authorization server. The link works once and for 10 minutes, and the authorization server shows its consent screen first. Recorded here and in the spec; binding the callback to a browser would need a session cookie the native apps cannot share with the system browser.
- **`PUBLIC_URL` is an origin.** `https`, or plain `http` on a loopback host only (redirect URIs must be `https` or `localhost`), without a path: the web app is served at the root. Unset, sign-in is off and the public routes answer `404`. `OAUTH_CLIENT_METADATA` (default `true`) exists because an install the authorization servers cannot reach (a home network, a VPN) would otherwise fail at any server that prefers Client ID Metadata Documents.
- **Clients learn the result by asking.** The callback redirects to `/oauth/done` (a web page that needs no session, linking back only a server id that looks like one); the web app reloads the server's page from there, and a native app, whose sign-in runs in the system browser, polls the server every 3 seconds for up to 10 minutes. No new user event type was added.
- **Not in this step.** Step-up authorization (re-signing in with the union of scopes after a `403 insufficient_scope`) is reduced to "sign in again"; token revocation at sign-out (RFC 7009) is not sent; dynamically registered clients are not reused between sign-ins.
