## Decisions

- **Gemini limits from the native list, not a native adapter.** The compatibility endpoint stays the wire protocol (ADR-005); only the model refresh reads Google's native list, which needs no new dependency and fails soft. `thinking` is read too, because it is a documented field of the same resource and the preset otherwise assumes every model thinks; `supportedGenerationMethods` is not used, since the compatibility list already decides which models exist.
- **Publish the tested image, not a rebuild.** The compose job is the image's test; rebuilding in the publish job would push bytes nobody tested. The image moves between the jobs as a gzip `docker save` artifact kept one day, and only the publish job holds `packages: write`. amd64 only: a multi-arch build needs QEMU or a second runner and doubles the build; it can come later without changing the install steps.
- **Manual runs rehearse the release jobs.** Tags cannot be pushed from these sessions, so both release jobs also run on `workflow_dispatch` and stop right before the step that writes (the push, the release). That exercises the artifact hand-over, the version check, the tags, the checksums, and the notes on every manual run.
- **`up -d --no-build` with a published image.** Compose tries to pull an image that a service can also build and quietly builds it when the pull fails; `--no-build` turns a mistyped or private image into an error instead of a local build under the release's name.
- **One release version.** The server image, the native apps, and the web app they bundle ship together, so one version covers them, kept in `workspace.package.version` and `apps/native/package.json` (Tauri reads the version from there). The web and contracts packages stay private `0.0.0`: they are never published on their own.

## Notes

- **Two compose projects are named `copilot`.** The developer's `docker-compose.yml` (project name from the directory) and `deploy/compose.yml` (`name: copilot`) share the project name, so running the deploy file from a development checkout replaces the development Postgres container (the data volumes differ, so no data is lost, but the database stops answering on `localhost:5432` until `docker compose up -d --wait` restores it). That happened once during this step, through a shell heredoc that ended early; the development container was restored from the root compose file with its volume and data intact, and the empty volume `copilot_postgres` that the deploy file created is left for the owner to remove (`docker volume rm copilot_postgres`; this session's permission check refused it). Renaming either project would orphan an existing volume, so both names stay; try the deploy file locally only with `-p <another name>`.
